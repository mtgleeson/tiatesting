# Pluggable datastore (H2, Postgres, and the seam for more)

### The problem

Tia stores its mapping, statistics and library-tracking data in a SQL database, and until this
feature the only option was H2 - every construction site did the equivalent of
`new H2DataStore(...)`, and the SQL emitted by the persistence layer was H2 syntax hardcoded
throughout (`MERGE INTO ... KEY(...)`, `AUTO_INCREMENT`, upper-cased identifier lookups). H2 is
still the right default - zero setup, no server to run, see the "Embedded vs server-mode H2
connections" chapter - but some teams already run a shared Postgres instance and would rather
point Tia at that than stand up a dedicated H2 server. Supporting that meant separating "what SQL
does this vendor speak" and "how do I open a connection to it" from the datastore logic itself.

### Architecture

Three pieces divide the responsibility:

- **`SqlDialect`** (`org.tiatesting.core.persistence.dialect`) - the vendor-specific SQL surface:
  `identityColumnDefinition()` (H2's `BIGINT AUTO_INCREMENT PRIMARY KEY` vs Postgres's `BIGINT
  GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`), `upsert(table, columns, keyColumns)` (H2's
  `MERGE INTO ... KEY(...)` vs Postgres's `INSERT ... ON CONFLICT (...) DO UPDATE`),
  `tableExists(connection, tableName)` (H2 folds unquoted identifiers to upper case, Postgres to
  lower case, so each dialect queries `DatabaseMetaData.getTables` with its own case), and `id()`
  (the stable id used for the `tiaDBDialect` override and in error messages). `H2Dialect` and
  `PostgresDialect` are the two implementations today. `JdbcDataStore` (the datastore
  implementation that replaced the H2-specific one) is written entirely against this interface -
  it has no vendor-specific branches of its own.
- **`ConnectionProvider`** (`org.tiatesting.core.persistence.connection`) - how to obtain a
  `java.sql.Connection`. `H2ConnectionProvider` carries H2's embedded-vs-server-mode split: engine
  options (`PAGE_SIZE`, `CACHE_SIZE`, `DB_CLOSE_DELAY`, `DB_CLOSE_ON_EXIT`) only in embedded mode,
  connection retry with backoff in server mode, and the graceful-`SHUTDOWN`-on-`close()` handshake
  needed before a forked test JVM can reopen the same embedded file (see the "Embedded vs
  server-mode H2 connections" chapter for why each of those exists). Both modes connect to a single
  fixed database - branch isolation is not this class's concern, see "Branch isolation: schema per
  branch" below. `JdbcConnectionProvider` is the generic counterpart every other vendor shares: it
  opens a connection via `DriverManager.getConnection(jdbcUrl, user, password)` and nothing else -
  no engine options, no retry. Postgres uses it as-is; a URL-addressable vendor with no H2-style
  embedded mode needs no provider of its own.
- **`DataStoreFactory`** (`org.tiatesting.core.persistence`) - the single place a caller asks for a
  `DataStore`, so build-tool plugins and test-runner listeners never construct
  `new JdbcDataStore(new H2Dialect(), ...)` (or any other vendor) directly. `fromConfig(dbFilePath,
  dbUrl, user, password, dialectOverride, branch)` resolves the dialect via `SqlDialectRegistry`,
  derives the per-branch schema via `BranchSchema.schemaName(branch)`, then branches: H2 gets an
  `H2ConnectionProvider` built from `H2ConnectionSettings`; every other resolved dialect gets a
  plain `JdbcConnectionProvider`, after `requireDriverPresent` confirms its driver class is on the
  classpath (see "The two-classpath driver model" below). Either way the resolved schema is passed
  into `JdbcDataStore`'s constructor alongside the dialect and connection provider.
  `fromSystemProperties(branch)` is the same resolution read from the `tiaDBUrl` / `tiaDBUser` /
  `tiaDBPassword` / `tiaDBFilePath` / `tiaDBDialect` system properties the forked test JVM receives.
- **`SqlDialectRegistry`** (`org.tiatesting.core.persistence.dialect`) - resolves a dialect id or
  JDBC URL to a `SqlDialect` instance, and is the single source of truth for "what does Tia
  support": `SUPPORTED_IDS` (`["h2", "postgres"]`, in the order they're listed in error messages)
  and `DRIVER_CLASS_NAMES` (a map from non-H2 dialect id to its fully-qualified JDBC driver class,
  e.g. `postgres` -> `org.postgresql.Driver`; H2 is deliberately absent because its driver is
  bundled with Tia). Both `forUrl` (URL-sniffing) and `forId` (explicit override) read from the
  same `SUPPORTED_IDS` list when they need to report what's supported, so the two paths can't drift
  out of sync with each other.

### Branch isolation: schema per branch

Both dialects also carry two schema-management methods: `createSchemaIfNotExistsSql(schema)` and
`selectSchemaSql(schema)` (H2's `SET SCHEMA "schema"`, Postgres's `SET search_path TO "schema"`).
`BranchSchema.schemaName(branch)` (`org.tiatesting.core.persistence`) derives the schema name Tia
uses for a given VCS branch: `tia_` followed by the branch lowercased with every character outside
`[a-z0-9_]` replaced by `_`, clamped to 63 characters (Postgres's identifier limit) - so
`feature/foo` becomes `tia_feature_foo`. `DataStoreFactory` derives this schema once, from the
`branch` parameter passed to `fromConfig` / `fromSystemProperties`, and threads it into
`JdbcDataStore`'s constructor.

`JdbcDataStore.getConnection()` is where isolation actually happens: on every connection it
acquires from the `ConnectionProvider`, it creates the branch's schema if needed (memoized per
datastore instance, since H2 requires a schema to exist before it can be selected) and then
selects it, so every unqualified statement on that connection resolves against the branch's own
schema rather than the vendor's default. This is why branch isolation lives above the
`ConnectionProvider` layer rather than inside it: both H2 and Postgres connect to one fixed
database - the file path or URL never varies by branch - and it's the schema, not the database,
that changes per branch. There is no `{branch}` token to configure in `tiaDBUrl` / `dbUrl`; the
schema is derived automatically from the VCS branch on every run.

Postgres does not create databases on Tia's behalf (that needs `CREATEDB`, a broader privilege
than Tia asks for) - the database named in `tiaDBUrl` must already exist, and the connecting role
needs `CREATE` privilege on it to create schemas. H2 has no such distinction: `H2ConnectionProvider`
already creates the embedded file (or, in server mode, the server creates the database given
`-ifNotExists`) on first use, and the branch schema is created inside it the same way as Postgres.

### URL-scheme dialect inference

`SqlDialectRegistry.forUrl(jdbcUrl, dialectOverride)` resolves the dialect in this order:

1. If `dialectOverride` (`tiaDBDialect` / `dbDialect`) is set, look it up by id (case-insensitive)
   via `forId` - this wins regardless of what the URL says.
2. Otherwise, sniff `jdbcUrl`: `null`/blank or a `jdbc:h2` prefix resolves to `H2Dialect`; a
   `jdbc:postgresql` prefix resolves to `PostgresDialect`.
3. Anything else throws `IllegalArgumentException` naming the URL and `SUPPORTED_IDS` (e.g.
   `Unsupported JDBC URL 'jdbc:oracle:thin:@x'. Supported dialects: [h2, postgres]`), and the same
   shape of error (naming the id instead of the URL) is thrown for an unrecognized
   `dialectOverride`.

So an unset `tiaDBUrl` / `dbUrl` is exactly what makes H2 the default: no URL configured means step
2 falls through to the blank case and resolves to `H2Dialect`, backed by an embedded file at
`tiaDBFilePath` / `dbFilePath`. `tiaDBDialect` / `dbDialect` exists for the cases URL-sniffing can't
cover - a vendor reachable through more than one URL scheme, or simply wanting the choice to be
explicit in config rather than implicit in a connection string.

### The two-classpath driver model

Tia bundles only the H2 driver (H2 is a `tia-core` compile dependency). For every other dialect,
the JDBC driver has to be supplied by the user - but "add the driver as a dependency" is not one
step, because Tia's own code runs on **two separate classpaths** for a single test run:

1. **The forked test JVM.** `TiaTestExecutionListener` (JUnit 5), `TiaJunit4Listener` (JUnit 4) and
   `TiaSpockGlobalExtension` (Spock) all call `DataStoreFactory.fromSystemProperties(branch)` from
   inside the JVM that Surefire/Failsafe/Gradle forks to actually run the tests. That JVM persists
   the coverage mapping and statistics at the end of the run. Its classpath is whatever the test
   project itself declares as a (test-scope) dependency - it has no visibility into the Maven or
   Gradle plugin's own classpath.
2. **The build-tool JVM.** `AbstractTiaMojo.buildDataStore` (Maven) and
   `TiaBasePlugin.buildDataStore` (Gradle) call `DataStoreFactory.fromConfig(...)` from inside the
   build tool's own process - the JVM running `mvn` or the Gradle daemon. This is where
   `select-tests`, the HTML/text reports, `reconcile`, and the library tasks (`libraries`,
   `library-publishes`, `library-pending-methods`) all run. Its classpath is the Tia plugin's own
   dependencies (a Maven plugin's `<dependencies>`, or whatever is on the Gradle plugin's
   `buildscript` classpath) - it has no visibility into the test project's dependencies either.

A driver added to only one side works for some operations and silently fails for others - e.g.
adding the driver to the test project's dependencies alone would let the forked JVM persist, but
`select-tests` (which decides which tests to run *before* the test JVM ever starts) would fail to
even open a connection. So a non-H2 dialect needs the driver declared **twice**: once as a
test-scope dependency in the project under test, and once as a dependency of the Tia plugin itself
(see the README's [Using a different database](../README.md#using-a-different-database) section
for the worked Maven `<plugin>`-scoped-dependency and Gradle `buildscript` classpath snippets).

**Why this can't be collapsed to one place.** The two JVMs are genuinely separate processes with
independent classpaths - there is no single dependency declaration in either Maven or Gradle that
puts a jar on both a project's test classpath and a plugin's own classpath at once. Bundling every
possible vendor's driver inside Tia itself (the way H2 is bundled) would avoid the two-classpath
requirement, but at a cost: it grows Tia's own dependency footprint for vendors most users never
touch, forks Tia's release cadence to every driver's own versioning, and risks a version conflict
for a user who needs to pin a specific driver version to match their database server. Requiring the
user to add the driver themselves, in the two places it's actually needed, keeps Tia's own
footprint at just H2 and gives the user control over which driver version they run.

**The missing-driver error.** `DataStoreFactory.requireDriverPresent` guards `fromConfig`'s non-H2
branch: it looks up the dialect's driver class via `SqlDialectRegistry.driverClassName(dialectId)`
and probes it with `Class.forName`. H2 never reaches this check - it's bundled, so `fromConfig`'s H2
branch returns before `requireDriverPresent` is called. If the probe fails,
`DataStoreFactory.missingDriverMessage` builds the actionable message:

```
Tia could not find the postgres JDBC driver on the classpath. Add the driver as a test-scope
dependency in your project AND as a dependency of the Tia plugin (see the pluggable-datastore
WIKI chapter).
```

Without this guard, a missing driver would instead surface many calls deeper, as an opaque
`No suitable driver found for jdbc:postgresql://...` `SQLException` thrown from inside
`DriverManager.getConnection` - correct, but uninformative about which of the two classpaths is
missing the jar.

### H2 as the default

`SqlDialectRegistry.forUrl` treats an unset or `jdbc:h2`-prefixed URL as H2, so a project with no
`tiaDBUrl` / `dbUrl` and no `tiaDBDialect` / `dbDialect` gets H2 with zero configuration - exactly
the pre-pluggable-datastore behaviour. `DataStoreFactory.fromConfig` special-cases H2 with its own
branch (`H2ConnectionProvider` + `H2ConnectionSettings`, embedded or server mode) precisely because
H2 is the only dialect with an embedded mode, connection retry, and the graceful-shutdown handshake
described in the "Embedded vs server-mode H2 connections" chapter; every other dialect shares the
plain `JdbcConnectionProvider`. H2 is also the only dialect exempt from the driver-presence check,
because it's a `tia-core` dependency rather than something the user has to add.

### The MySQL seam

MySQL is not implemented, but the registry is shaped so adding it is small and contained. A future
`MySqlDialect` would need to:

1. Implement `SqlDialect`: `identityColumnDefinition()` (MySQL's `BIGINT AUTO_INCREMENT PRIMARY
   KEY`, similar to H2's), `upsert(...)` (MySQL's `INSERT ... ON DUPLICATE KEY UPDATE`), and
   `tableExists(...)` (MySQL's identifier case-folding is platform-dependent, unlike H2's and
   Postgres's fixed rules, so this needs its own care).
2. Add `"mysql"` to `SqlDialectRegistry.SUPPORTED_IDS` and a `mysql` -> driver-class-name entry
   (e.g. `com.mysql.cj.jdbc.Driver`) to `DRIVER_CLASS_NAMES`.
3. Add a branch to both `forUrl` (a `jdbc:mysql` prefix) and `forId` (the `"mysql"` override) so
   the URL-sniffing and explicit-override paths both resolve it.
4. Nothing else changes: `DataStoreFactory.fromConfig`'s non-H2 branch, the driver-presence check,
   and `JdbcConnectionProvider` all already work for any vendor reachable through a plain JDBC URL
   with no embedded mode - MySQL would fall straight into that path the same way Postgres did.
